# Word Card 项目 Git 规范

> 版本：1.0.0  
> 更新日期：2026-06-11  
> 参考标准：Conventional Commits (约定式提交)

---

## 1. 提交消息规范

### 1.1 消息结构

```
<type>(<scope>): <subject>

[可选 body]

[可选 footer]
```

**语言要求**：提交消息（标题与正文）必须全部使用**中文**编写。

### 1.2 标题行（必填）

**格式**：`<type>(<scope>): <中文简述>`

**type 类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | 新增组件、外设驱动、Demo 等 |
| `fix` | Bug 修复 | 修复死锁、内存泄漏、引脚配错等 |
| `refactor` | 重构 | 代码逻辑优化、目录重排，不改功能 |
| `docs` | 文档变更 | 更新 README、开发规范等 |
| `test` | 测试相关 | 新增单元测试或验证用例 |
| `chore` | 构建/工具变更 | 修改 CMakeLists、.clang-format、配置 Kconfig 等 |
| `style` | 格式修正 | 仅格式化代码、空格/换行调整，不影响逻辑 |
| `perf` | 性能优化 | 降低 RAM/Flash 占用、优化 CPU 执行效率 |

**scope 影响范围**：

| 范围 | 说明 |
|------|------|
| `arch` | 顶层架构设计、构建系统配置、工具链集成 |
| `bsp` | 板级支持组件 (`components/bsp`) |
| `driver` | 外设驱动组件 (`components/dev_devices`) |
| `main` | 主应用层逻辑 (`main/`) |
| `docs` | 项目文档 |

**subject 要求**：
- 使用中文编写
- 不超过 50 个字符
- 结尾不加句号
- 使用祈使语气（例：“新增 bsp_lcd 驱动” 而非 “新增了bsp_lcd驱动”）

### 1.3 示例

```
feat(bsp): 新增 bsp_lcd 模块以驱动 ST7789 显示屏

- 在 components/bsp 中编写板级 LCD 服务接口
- 绑定 ESP32-S3 的 SPI2 总线
- 配置背光 GPIO 并支持软件 PWM 调光

验收: idf.py build && idf.py flash
```

## 2. 分支模型与合并工作流规范

为了理清各分支之间的开发与集成关系，防范黑盒合并带来的代码冲突与历史树混乱，特制定以下分支与合并规范：

### 2.1 分支定义与职责

| 分支 | 职责与保护级别 | 备注 |
| :--- | :--- | :--- |
| **`main` / `master`** | **主生产分支**。受保护分支，只接收从 `develop` 分支发起的稳定合并，代码必须可随时用于生成发布版本。 | 严禁直接在该分支提交或强制推送。 |
| **`develop`** | **开发集成分支**。各阶段里程碑功能的物理汇总分支，代表当前正在整合且测试中的开发代码。 | 由功能分支开发完成后合并至此。 |
| **`feature/<里程碑>-<描述>`** | **功能开发分支**。临时分支，专门用于单个里程碑功能模块的闭环开发。 | 开发完成后即可销毁。 |
| **`hotfix/<描述>`** | **热修复分支**。用于紧急修复生产环境 (`main`) 爆发的重大 Bug。 | 修复后需同步合并回 `main` 和 `develop`。 |

### 2.2 功能分支流转契约 (流转三原则)

#### 1. 必须切自 `develop`
- 所有的功能开发分支（`feature/`），**必须且只能从最新的 `develop` 分支拉取和检出**：
  ```bash
  git checkout develop
  git pull origin develop
  git checkout -b feature/m1-lcd-driver
  ```

#### 2. 非快进合并 (`--no-ff`)
- 当完成规划中当前里程碑的开发后，合并回 `develop` 分支时，**必须采用非快进模式（Non-Fast-Forward）**。
- 这能确保在 Git 历史树中清晰地生成一个合并节点，完整保留整个 feature 分支的演进轨迹，极大利于故障回滚：
  ```bash
  git checkout develop
  git merge --no-ff feature/m1-lcd-driver
  ```

#### 3. 严格的人工授权与权限分工
- **合并指令执行权**：合并命令（如 `git merge`）**只能由开发者手动下达**，或者由开发者在对话中明确授权 Agent 执行，Agent 绝不能自主触发合并动作。
- **远程推送推送权**：当本地 `develop` 分支合并完成后，如果需要推送至远程仓库（`git push`），**必须征得开发者明确授权**，Agent 绝对禁止静默执行远程推送。

## 3. 原子化提交约束 (Atomic Commit Constraints)

为了保障代码历史的可追溯性、易回滚性及清晰的开发路径，所有提交必须遵循**原子化**与**顺序化**原则：

### 3.1 按开发顺序提交
- 提交必须严格契合实际开发演进的先后步骤，依次进行提交。
- **典型开发提交顺序**：
  1. `chore(arch)`: 引入第三方库、配置 CMake / Kconfig。
  2. `feat(driver)`: 编写低层芯片驱动代码。
  3. `feat(bsp)`: 编写板级服务绑定引脚。
  4. `feat(main)`: 编写业务逻辑或调度任务。
  5. `docs(docs)`: 补充或修补文档。

### 3.2 按操作类型分离 (严禁混淆提交)
- 一个提交只能专注于一种操作类型。**严禁在同一个 Commit 中一次性提交多种类型的修改**。
- **禁止的行为示例**：
  - ❌ 在同一个提交中，既新增了 LCD 驱动功能 (`feat`)，又顺便把按键驱动的格式规范化了 (`style` / `refactor`)。
  - ❌ 在同一个提交中，既修复了某处死锁 Bug (`fix`)，又修改了 CMakeLists 构建逻辑 (`chore`)。
- **正确的处理方式**：必须使用 `git add -p` 或分批 `git add <file>`，将不同性质的改动拆分为多个独立的、粒度微小的 Commit 依次提交。
- **可编译原则**：拆分后的每一次原子提交，都必须保证项目运行 `idf.py build` 能够编译成功，禁止提交破坏编译树的中间状态代码。

## 4. 开发提交检查清单 (Checklist)

在向本地或远程提交代码前，确保：
1. **原子化自检**：检查当前提交是否只包含单一类型和逻辑步骤的改动。
2. **编译测试**：代码必须在本地运行 `idf.py build` 编译成功，且无严重编译器警告。
3. **格式化**：代码已通过 `.clang-format` 完成格式整理。
4. **安全约束**：绝不由 AI Agent 自动进行 `git commit` 或 `git push`，必须展示 Diff 并经开发者手动确认。
